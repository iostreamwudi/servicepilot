## 1. 项目定位

ServicePilot 是面向企业客服与 AI 服务治理的智能客服平台原型/验证项目，目标不是单一聊天机器人，而是连接：

消费者提问 → Agent 意图识别/知识检索/工具调用 → 风险判断 → 人工客服接管 → 工单与结案 → 知识、质检和策略优化。

当前产品优先级是先打通“真实问答与人工接管”主链路，再逐步将知识、评测、策略、权限和审计模块生产化。

当前页面业务数据中，除真实问答、会话、客服回复、知识查询/建设相关链路外，部分运营指标、审批和分析数据仍是可交互 mock 数据；但按钮必须有真实的前端状态变化、导航、筛选、导出、弹层或 API 操作。

## 2. 用户与角色

### 2.1 消费者/体验用户

消费者端是测试输入端，不是后台系统的核心使用者。

- 可选择测试身份：普通消费者、会员用户、高风险投诉用户。
- 可创建、新建、切换长期保存的会话。
- 可进行真实多轮提问。
- 可收到 Agent 回复和一线客服人工回复。
- 不展示 Agent、模型、置信度、知识来源等内部术语，保持真人客服体验。

### 2.2 一线客服

核心任务是接管 AI 无法安全处理的会话：

- 查看待接管、处理中、等待内部、已解决会话。
- 查看完整历史消息、AI 摘要、订单事实、风险和 SLA。
- 接管会话、发送人工回复、创建/跟进工单、升级主管、结案和重新打开。
- 使用 AI 回复建议、引用已发布知识、反馈摘要问题。

### 2.3 服务主管

- 查看运营总览、风险、SLA 和跨角色动态。
- 查看或调度工单和高风险事项。
- 关注服务质量、人工接管和业务异常。

### 2.4 知识运营

- 管理知识缺口、冲突、待复核和资产库。
- 导入官方政策、内部规范和 FAQ。
- 编辑知识草稿、测试真实问法、提交双人复核、灰度发布和回退。
- 管理预设回复/话术资产，为 Agent 提供表达上下文。

### 2.5 AI 运营

- 运行真实模型回归/盲测。
- 查看失败案例和人工复核队列。
- 将失败案例回流知识、策略或数据治理任务。
- 配置风险转人工、置信度阈值、模型路由和发布策略。

### 2.6 系统管理员/治理人员

- 管理企业空间、成员、角色和资源权限。
- 管理任务→接口→指标资源树。
- 查看权限来源、继承和冲突。
- 查看审计记录并导出。

## 3. 已完成的真实主链路

### 3.1 用户提问到 Agent

入口：后台顶部“体验用户端”。

主要代码：

- `app/page.tsx`：消费者体验端和后台界面。
- `app/api/agent/respond/route.ts`：Agent 处理入口。
- `lib/intent-router.ts`：意图、风险、转人工和可解释信号。
- `lib/order-tool.ts`：只读订单/退款工具。
- `app/api/tools/order-refund/route.ts`：订单工具 API。

处理顺序：

1. 读取当前测试租户和会话历史。
2. 对输入做意图识别、风险判断和上下文理解。
3. 检索审核生效知识。
4. 对订单/退款类请求调用白名单只读工具。
5. 调用当前配置的真实生成模型（现为GLM-5.2非思考模式）生成回答。
6. 进行输出校验，必要时生成转人工任务。
7. 将用户消息、Agent 消息、知识引用、工具调用和状态写入数据库。

模型不可用时必须返回明确异常，不得静默生成伪造客服回答。

### 3.2 人工客服回传用户端

- 用户消息和客服消息均写入消息表。
- 会话中心读取完整历史，不再只显示最新一条消息。
- 用户端轮询会话，可收到客服回复。
- 会话长期保存，不再依赖 30 分钟临时缓存。

### 3.3 知识库

- 知识资产有来源、版本、状态、责任团队、风险和覆盖率。
- Agent/客服只引用 `active` 生效知识。
- 导入资料先生成草稿/待复核，不绕过审批直接上线。
- 已有生成数据和官方来源数据位于 `data/` 与 `data/generated/`。

### 当前检索架构判断（2026-08-20）

当前 Agent 链路不是标准向量 RAG，也不是 Agentic RAG/Graph RAG：它采用规则与概率意图分类，随后按业务类别从数据库读取 active 知识，以关键词命中打分、默认知识兜底，最后调用 Qwen 生成；退款问题可追加只读订单工具。知识层级映射仅用于治理评测，不是图谱检索。

方案决策：进入检索架构升级阶段，但按 Hybrid RAG → Agentic RAG →（必要时）Graph RAG 的顺序推进。先用 Embedding 召回、关键词召回、元数据过滤和重排解决知识来源失败；再让 Agent 处理低置信度澄清、检索重试、多知识组合和工具编排。Graph RAG 只有在订单/商品/规则/流程关系稳定沉淀后再评估，不能为了技术名词提前引入。

### 面向小白的优化解释

- 多轮上下文：让系统记住前一句的主题。例如先问“发票抬头错了”，再问“什么时候能好”，系统知道“好”指发票。
- 复合意图：一句话有多个诉求时先处理主要动作。例如“地址填错了，可以拒收然后退款吗”，先处理地址/拒收，再说明退款。
- 父子知识：允许更具体的流程回答大类问题。例如明确问“能维修吗”时命中维修知识是正确的；只说“丢件”却命中维修知识仍是错误。
- 转人工：遇到高风险、需要订单状态或超出知识范围的问题，不让模型硬猜。例如旧 SIM 卡能否用于新手表，应转给人工确认。
- 评测治理：区分“模型真的答错”和“评测标准太死”。合理命中子知识不能再被机械判错，但真实错误仍保留。
- Hybrid RAG：像搜索引擎同时看关键词和语义。例如“钱还没回来”和知识里的“退款到账”字面不同，但语义相近，混合检索更容易找对答案。

### 当前线上方案的技术细节

当前意图识别分三层：先用业务规则匹配退款/破损/地址/发票的强关键词和表达模式；再把问题与最近历史切成 2～4 字片段，输入本地 TF-IDF/线性概率分类器，得到各业务和范围外的概率；最后结合结构化会话主题。规则分数、概率分数和复合意图加分会一起排序，分差过小则不强行路由。

知识检索发生在意图识别之后：从 `knowledge_documents` 中筛选同一业务类别且 `state=active` 的文档，去掉用户问题空格/标点，逐条检查 `keywordsJson` 中的关键词是否出现。通用关键词低权重，专门关键词高权重，默认父知识有少量兜底分；得分最高的知识正文交给 Qwen 生成回答。当前线上链路没有使用向量检索。

例子：“发票税号写错了怎么改”会先被识别为发票，再只在发票 active 知识中检索，“税号/修改发票”等专门词让 `KB-402` 排名靠前，最后由 Qwen 组织成客服回复。真实向量模型已经进入生产影子链路，但不向 Qwen 提供知识、不替换回答来源；纯向量通过率仅 46%，因此继续只作为 Hybrid 候选证据。

1. **补齐知识生命周期**：建立草稿 → 待复核 → 已批准 → 灰度 → 全量生效 → 回滚/归档的不可变版本链；保存创建人、修改人、审核人、发布时间、回滚原因和影响范围。
2. **补齐真实版本 Diff 和并发保护**：支持当前草稿与线上版本对比，使用版本号或 `If-Match` 防止多人覆盖修改；离开未保存页面时必须提醒。
3. **补齐来源治理**：保存来源文件/页面、来源版本、抓取时间、快照地址、内容哈希、同步状态和责任团队；“查看来源快照”不能只是提示消息。
4. **补齐有效期治理**：知识查询列表当前按 `state=active` 查询，但没有在管理列表层按 `validFrom/validUntil` 过滤；界面已有检索层有效期判断能力，管理端仍需显示已过期、即将过期和未生效状态，避免客服看到不可引用内容。
5. **禁止硬编码运营指标**：知识缺口、口径冲突、待复核、影响会话、灰度流量和发布影响预估当前存在固定演示数据。必须来自真实反馈、检索、会话、版本和发布数据，并显示统计口径、数据时间和数据来源。
6. **冲突和重复检测**：导入或编辑时检测同类知识、父子知识、互相矛盾的时效/金额/条件表述；支持冲突负责人、处理意见、适用范围和关闭记录。
7. **审核证据完整化**：发布前应强制展示真实用户问法、召回结果、回答边界、人工接管结果和风险检查结果；审核通过必须绑定测试运行 ID，而不是仅显示“3/3 通过”。
8. **补齐回滚和灰度观察**：灰度发布需要真实流量比例、观察窗口、成功/失败指标、异常告警和一键回滚；回滚必须记录原因和操作者，不能只显示“可随时回退”。

### 71.3 P1：搜索、列表和前端数据层

1. **搜索升级为企业级检索**：当前主要是 SQL `LIKE` 模糊查询，未覆盖关键词字段，也没有全文索引。应使用 FTS 或专用检索索引，支持标题、正文、关键词、来源、负责人、版本和知识编号，并提供命中词高亮和相关度说明。
2. **减少列表接口过度传输**：知识列表当前直接返回完整正文，列表只需要摘要；正文应通过详情接口按需加载，降低数据暴露和首屏负载。
3. **补齐搜索体验**：增加搜索建议、最近搜索、常用问法、零结果推荐、清除条件、相关知识和“反馈知识缺口”路径。
4. **修复请求竞态**：前台知识查询和知识运营查询请求没有 `AbortController` 或请求序号保护；快速输入、切换分类或翻页时，旧响应可能覆盖新结果。应增加取消、序列号和卸载清理。
5. **保存查询上下文**：搜索词、分类、状态、页码、排序、选中知识和视图应写入 URL 或可恢复状态，支持刷新、复制、通知跳转和浏览器返回。
6. **完善分页和排序**：客服查询页目前固定每页 12 条；应支持 25/50/100、页码跳转、更新时间/相关度/覆盖率排序，并在结果区明确当前条件和结果总数。
7. **避免脆弱事件处理**：知识运营筛选通过 document 级事件监听和按钮文案匹配来切换状态，容易因文案变化失效；应改为组件内显式 React handler，并使用稳定的状态值。
8. **后端查询性能**：正文 `%query%` 查询在知识量增长后会退化；需要索引、全文搜索、合理的统计聚合、并行查询和可观测的查询耗时。当前返回约 1,533 条知识总量、25 条生效知识，应以更大数据量做压测。

### 71.4 P1/P2：UI、交互和可访问性

1. **筛选语义**：分类和状态按钮补充 `aria-pressed` 或改为语义明确的 tab/单选控件；当前 active 主要依赖颜色和 CSS 类。
2. **运营 tab 语义**：工作队列、知识资产、话术训练和编辑 tab 统一补充稳定 ID、`aria-selected`、`aria-controls`、键盘方向键和焦点回移。
3. **结果列表可读性**：知识卡片当前将标题、摘要、来源和编号组合成很长的无障碍名称；应拆分可读标题、摘要和辅助信息，避免屏幕阅读器重复播报大量正文。
4. **来源新鲜度可视化**：详情页增加最后同步、来源版本、有效期倒计时、快照状态和可信度，不只显示来源名称。
5. **空状态与错误恢复**：区分无搜索结果、无生效知识、接口失败、权限不足和数据过期；每种状态提供清除筛选、重试、申请权限或反馈缺口的下一步。
6. **操作反馈真实化**：保存、导入、测试、提交、发布、回滚和反馈都必须显示加载、成功、失败、重试和部分成功状态；禁止仅 Toast 宣称完成。
7. **未保存保护**：编辑内容、风险等级、人工接管和话术字段被修改后，关闭、切换知识或切换页面需要提醒并支持恢复。
8. **视觉细节**：运营页的部分辅助文字小于 10px，建议提升可读字号和对比度；刷新、关闭等控制使用统一 SVG 图标系统，避免系统字符在不同平台显示不一致。
9. **保持已有优点**：保留当前搜索入口、双栏查询布局、详情元数据、反馈入口、空状态、skip link、`aria-live`、弹层焦点管理和 reduced-motion 支持。

### 71.5 P1：新增企业 SaaS 功能

2. **知识影响分析**：命中次数、零结果率、负反馈率、引用率、转人工率、相关会话、版本前后对比和成本影响。

4. **导入中心**：文件/链接导入、格式解析、切片预览、重复检测、敏感信息检测、冲突检测、导入报告和失败重试。
