# CSDS 全量知识库覆盖盘点

## 目的与边界

本盘点在当前 `kimi-k3` 评测进程运行期间独立完成，不修改 Router、Retrieval、RRF、Reranker、阈值或生产部署，也不改变正在运行的 4,196 条评测任务。

原始 CSDS 数据包含 10,701 个对话、277,399 个对话轮次和 21,126 个带标注 QA 问题。一个对话可能包含多个业务问题，因此“对话数”不能直接等同于“可评测问题数”。

当前 4,196 条评测集是从这些 QA 中筛出的唯一问题，范围限于现有知识库可以明确映射的四个主类：退款、发票、地址、破损/质量。全量盘点不把上游 intent 直接当成知识条目；上游标签存在混合意图和粒度不一致，必须经过业务归并和人工审核。

## 第一批建议建设顺序

1. **履约与物流**：覆盖量高，且与现有 `KB-301` 地址知识边界最容易混淆。优先拆出配送周期、出库/发货、物流跟踪、拒收/拦截、签收异常、预约配送和配送方式。
2. **订单生命周期**：补齐取消、修改、订单状态、订单异常、拆分/合并、恢复和预售。每条知识必须区分“咨询规则”和“需要查询订单事实”。
3. **售后扩展**：在现有 `KB-114`、`KB-208` 族之上补齐售后单、退换货处理周期、审核不通过、维修点、纠纷单、少件/丢件和售后运费。
4. **促销与权益**：价保、优惠券、礼品卡、赠品和活动规则通常需要实时活动配置，知识条目必须包含生效期、适用商品/订单条件和转人工条件。
5. **商品与服务、支付账户、商家服务**：这些域的正确答案高度依赖商品、账户或商家实时数据，应采用“规则知识 + 受控查询/转人工”的组合，而不是只写静态 FAQ。

## 知识条目建设规则

- 每个候选条目使用独立 `knowledgeId`、标题、正文、关键词、适用条件、排除条件、所需事实字段、风险级别、负责人、版本和来源。
- CSDS 的客服回答只能作为“观察到的历史话术/候选证据”，不能直接当作当前业务规则；涉及时效、赔付、支付、税务、会员权益的内容必须由业务负责人确认。
- 对一个上游 intent 出现多个真实业务问题的情况，按“问题 + 动作 + 状态 + 所需事实”拆分，而不是一类一个文档。例如“配送周期”中混有物流时效、退货运费和会员问题，不能合并为一个知识条目。
- 新条目先进入 `review` 候选区，人工确认后才允许进入 active 知识库和评测 `expectedSource` 映射。
- 没有可靠业务依据的问题先标记 `unsupported/no_knowledge`，不为了提高覆盖率编造答案。
