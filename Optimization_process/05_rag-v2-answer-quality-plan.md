# Step 8｜RAG v2 多阶段证据检索与回答质量优化

## 1. 优化范围

本阶段只优化会直接改变 Agent 回答效果的技术能力：问题理解、知识召回、候选排序、证据组织、事实校验、追问和转人工。不更换生成模型，不继续扩建影子复核工作台、灰度控制面、监控后台、RBAC 或灾备。现有影子链路保留为验证工具，不作为本阶段交付目标。

当前生产回答仍是“规则/概率意图路由 + D1 active 知识 + 字符串关键词匹配”；动作感知 Hybrid 已在影子链路运行，尚未接管生产回答。

## 2. 冻结基线与指标口径

| 指标 | 当前基线 | 口径 |
|---|---:|---|
| 完整 Agent 回归 | 78/100（78%） | 知识来源、转人工、必要信息和禁止内容联合通过 |
| 高风险通过率 | 100% | 高风险、安全和对抗样本 |
| 现网候选层级可接受来源 | 86/100（86%） | Step 7 动作重排实验的候选层口径 |
| 动作重排 Hybrid 候选 | 89/100（89%） | 候选层结果，不等同于完整 Agent 通过率 |
| 冻结盲测总体 | 44/55（80%） | 40 条未观察真实语料 + 15 条安全门禁 |
| 上下文依赖盲测 | 3/10（30%） | 当前最明显的回答能力短板 |

每个实验必须冻结生成模型、Prompt、知识版本、向量索引版本和评测集；若其中任何一项变化，必须单独建基线，禁止混算。

## 3. 目标技术架构

```text
用户问题
  → 上下文查询重写
  → 任务/动作/条件解析
  → 检索路由
      ├─ BM25 稀疏检索
      ├─ Dense 向量检索
      ├─ 结构化决策表
      └─ 业务工具
  → RRF 候选融合
  → 父子知识/前置条件/排除条件重排
  → Top-K 证据包 Evidence Pack
  → 回答规划
  → Claim–Evidence 事实与完整性校验
  → 回答 / 追问 / 转人工
```

## 4. Step 8.1：BM25 稀疏检索

状态：已完成离线实现与对照，保留为下一阶段候选召回能力，未接入生产回答。

### 问题

当前字符串包含匹配把“退款”“怎么”等通用词和“税号”“红冲”等高区分度词主要依靠手工权重处理，不能自然利用词频、文档频率和文档长度。

### 技术方案

- 索引 active 知识的分词、词频、文档频率、平均文档长度和版本信息。
- 使用 BM25 替代简单字符串关键词分，但保留命中词解释。
- 在当前 25 份知识规模下继续使用 D1/应用内计算，不为了技术名词引入 Elasticsearch。
- 分别输出 current lexical、BM25、dense 和后续 fusion 结果，禁止提前覆盖稳定检索。

### 示例

用户问：“发票税号填错了怎么处理？”“税号”的区分度应明显高于“怎么”“处理”，优先召回税号修改知识，而不是通用发票申请知识。

### 验收

- 同一 100 条候选集与当前关键词方案逐条对比；
- 严格来源和层级可接受来源均记录；
- 典型改善、退化和中性互换逐条归因；
- 高风险及范围外路由不得受影响。

### 实际结果

- 实现版本：`bm25-step8.1-v1`；数据集：`1.0-real85+0.1-seed15`，100条；知识版本：`2026.07.2`。
- 现网关键词复算：严格来源67/100、层级可接受86/100。
- 第一轮纯BM25：严格来源60/100、层级可接受75/100；20条来源变化中改善1、退化12、中性7。正文里的“客服、公司、收到”等稀有但无业务决策价值的词把具体子知识错误推高。
- 移除 `[数字]`、`[地址]` 等脱敏占位符后，纯BM25为严格61/100、层级可接受76/100，仍不通过；例如 `[数字]` 曾错误匹配“数字商品”。该失败实验保留，纯BM25不允许单独上线。
- 最终采用“BM25召回＋已有业务动作/父子门控”：严格来源69/100、层级可接受88/100；相对现网改变5条，改善2、退化0、中性3。
- 21条上下文依赖样本仍为严格12/21、层级可接受14/21，与现网持平，说明BM25不能解决省略和指代，需由Step 8.3查询重写处理。
- 本地检索平均0.155ms、P95 0.284ms、最大0.971ms；构建通过，38/38自动化测试通过。

改善示例一：“地址填错了……突然发现签收了”，现网被“填错”推到 `KB-302` 收件人信息，BM25＋动作门控回到 `KB-301` 地址父知识。改善示例二：“电视能修吗；液晶屏坏了”，现网选择 `KB-214`，但“能修”未达到现有维修子知识接受规则；新方案选择 `KB-208` 父知识。中性示例：“退货后发票多久能改过来”由父知识 `KB-401` 切到满足明确退货发票动作的 `KB-404`，两者均为可接受来源。

决策：BM25本身不能替换现网关键词；将其作为可解释稀疏召回信号保留，下一步进入Step 8.2结构感知父子切片。共享构建产物已部署腾讯云，但未在生产选择器中调用BM25；首页、Agent健康接口和影子查询均为HTTP 200，历史现网/影子来源仍为`KB-302`/`KB-301`。部署前备份为`/opt/servicepilot/backups/pre-bm25-7671eaa-dist.tar.gz`。生产回答、Prompt、转人工和完整Agent 78/100基线均未改变。

## 5. Step 8.2：结构感知父子切片与 Contextual Retrieval

### 问题

整份知识向量容易稀释局部主题；机械定长切片又会丢失业务、阶段和适用条件。

### 技术方案

- 按标题、业务阶段、前置条件、步骤、时效、异常分支和排除条件切片。
- 子切片负责召回，命中后回读父知识的必要上下文。
- 生成向量和 BM25 索引前，为短切片补充业务、流程、主题和适用条件。
- 显式保存 `parentId`、`action`、`prerequisites`、`exclusions` 和版本，不再只靠代码猜父子关系。

### 示例

原切片只有“通常在 1—3 个工作日到账”，容易与赔付或开票时间混淆。增强后变为“业务：退款；阶段：审核通过后的原路退回；正文：通常在 1—3 个工作日到账”，再参与检索。

### 验收

- 退款到账/退货规则、发票申请/税号修改、地址修改/手机号修改等相邻知识混淆减少；
- 子切片命中后引用可追溯到父知识和有效版本；
- 无前置条件证据时，具体子知识不得抢占通用父知识。

### 实施与结果（2026-08-21）

- 实现 `contextual-step8.2-v1`：按完整句切分知识，为每个切片补充业务类目、父知识标题、知识主题、段落类型、关键词和原文；保存 `documentId`、`parentDocumentId`、切片位置及最佳证据，切片召回后聚合回原知识文档。本步只做离线候选实验，未接入生产选择器。
- 数据审计发现25份active知识都很短，正文仅58—87个中文字符，其中22份只有2句。简单句子切片在固定100条上相对Step 8.1产生0条来源变化、0改善、0退化；平均耗时由0.161ms增至0.244ms，P95由0.285ms增至0.427ms。因此保留代码和失败记录，不上线句子切片。
- 结构审计发现`KB-211`“签收验货与留证”遗漏了与`KB-208`“商品破损或异常”之间的父子关系。补齐后，只有当前问题明确出现“签收、验货、外包装、拍照、留证、证据、拒收”等动作时才允许`KB-211`晋级；否则回到父知识。
- 最终结果：严格来源70/100、层级可接受89/100，较Step 8.1的69/100、88/100各提高1点；相对现网共5条变化，3改善、0退化、2中性。21条上下文依赖样本由Step 8.1的严格12/21、可接受14/21提高到13/21、15/21。
- 改善示例：“发现有很大的哨声，刺耳”过去因泛词“发现”误选`KB-211`，补齐父子动作门控后回到`KB-208`；而“外包装破损，签收时怎么拍照留证”仍可选择`KB-211`。这说明本轮收益来自结构化父子约束，不是切片本身。
- 决策：采用新增父子关系和动作门控作为Step 8.2胜出变更；句子级Contextual Retrieval不接生产。完整Agent、Prompt、转人工及生产回答来源均未改变，完整Agent仍沿用78/100、高风险100%的冻结基线。下一步进入Step 8.3多查询召回与RRF，优先处理其余多数因`routeIntent=null`造成的上下文失败。
- 验证：完整构建和41/41自动化测试通过；本步没有改变产品角色、用户流程、权限、生产指标或发布行为，因此不更新PRD。
- 完整Agent回归：通过`router-v2.3-step8.2-contextual-eval`评测开关，使用同一100条生产评测集真实调用`qwen3.7-plus`。新方案总体79/100（79%）、高风险83.3%、平均延迟8657ms；生产基线总体78/100、高风险100%、平均延迟8518ms。总体仅升1个百分点，但高风险下降、延迟增加，因此不能接管生产。后续统一报告这三项生产评测指标及失败归因；检索层数字只作为内部诊断，不作为方案通过率。

## 6. Step 8.3：多查询召回与 RRF 融合

### 问题

只使用用户最后一句检索时，“审核过了怎么还没到”等省略表达缺少完整业务信息；BM25 分数和向量相似度也不适合直接固定权重相加。

### 技术方案

- 同时检索原始问题、上下文补全问题和结构化任务查询。
- 使用 Reciprocal Rank Fusion 按候选排名融合 BM25 与 Dense 结果，避免不同分数量纲直接相加。
- 查询重写只补充会话中已经确认的事实，不得生成用户未提供的订单状态或条件。

### 示例

用户上一轮说“退款已经审核通过”，本轮问“怎么还没到”。检索查询可补全为“退款审核通过后仍未到账”，但不能擅自补充“银行卡已注销”。

### 验收

- 上下文依赖样本单独统计，目标由 30% 向至少 60% 推进；
- 独立单轮样本不得因上下文污染下降；
- 对每个新增查询保存来源和补全依据，便于复盘。

### 实施结果（2026-08-21）

- 评测分支实现三路确定性查询：原始问题、仅使用已确认会话事实的上下文问题、结构化业务问题；每路使用Contextual BM25召回，再以RRF按排名融合，之后保留父子动作门控。
- 同一100条完整Agent评测结果：总体77/100（77%）、高风险83.3%、平均延迟8540ms；生产基线78%/100%/8518ms，Step 8.2为79%/83.3%/8657ms。
- 本轮不通过：总体下降1个百分点，高风险仍比生产低16.7个百分点；知识来源失败14条、转人工失败10条、必要信息缺失5条、禁止内容1条。
- 失败判断：RRF把多个查询中的泛化上下文证据累加，未提升省略问题，反而把部分错误候选推高；评测开关已撤回，生产未切换。
- 下一步不是直接进入Step 8.4，而是先做Step 8.3修正版：限制上下文查询只在路由置信度和已确认事实同时满足时启用，并设置原始查询保护权重，再用同一完整Agent评测复测。

### Step 8.3 修正版结果

- 原始问题权重3倍；无已确认会话事实时只使用原始查询；结构化查询权重0.5倍。
- 完整Agent结果：总体76/100（76%）、高风险66.7%、平均延迟8581ms；仍低于生产基线78%/100%/8518ms。
- 结论：两版RRF均不通过，评测开关已回滚。下一步暂停RRF，转向条件精排与证据约束，优先恢复高风险100%。

### Step 8.4 证据约束结果（2026-08-24）

- 保持生产关键词检索和转人工策略，仅在评测生成阶段加入条件、排除项、时效、材料和无依据承诺检查。
- 完整Agent结果：总体77/100（77%）、高风险83.3%、平均8767ms；生产基线78%/100%/8518ms。
- 知识来源失败14条、转人工失败10条、必要信息缺失5条、禁止内容1条；未改善主要bad case。
- 结论：单纯生成前证据约束无效且增加延迟，评测开关已回滚。下一步改为逐条bad case确定性条件规则，不再继续堆叠通用Prompt约束。

### Step 8.5 确定性 bad case 规则结果

- 针对固定必要信息失败增加规则化提示：退款时效、生鲜拆封限制、发票详情路径、范围外标准话术。
- 完整Agent结果：总体78/100（78%）、高风险100%、平均8975ms；生产基线78%/100%/8518ms。
- 必要信息失败从5条降至2条，高风险恢复100%，但延迟增加457ms，因此不直接接生产。
- 下一步：将规则从额外长提示改为本地答案结构校验或短提示注入，目标保持78%以上、高风险100%，并把平均延迟压回8518ms以内。

## 7. Step 8.4：条件精排与 Corrective RAG

### 问题

候选相关不等于能够回答。向量可能找到相似知识，但不满足当前业务阶段、动作或排除条件。

### 技术方案

- 第一层硬过滤租户、active、有效期、类目和权限。
- 第二层用 BM25、Dense、RRF 保证正确知识进入 Top-K。
- 第三层按意图、动作、前置条件、排除条件、父子关系和第一/第二名分差精排。
- 高置信候选直接进入证据包；低置信时最多允许一次查询改写和纠错检索；仍不可靠则追问或转人工，不允许自由循环。

### 示例

“地址写错了，已经发货”必须先检查“已发货”条件，不能因为“修改地址”语义相似就直接给出未发货修改入口；系统应选择已发货后的拦截/拒收规则或追问物流状态。

### 验收

- 候选层级可接受来源超过当前 89/100 后才允许进入完整 Agent 对照；
- 相对现网的每条变化都要归类为改善、退化或中性；
- 范围外误路由不增加，高风险保持 100%。

## 8. Step 8.5：Evidence Pack 与 Claim–Evidence 校验

### 问题

即使知识找对，回答仍可能漏掉条件、时效和下一步，或把通用政策误写成用户个人状态。

### 技术方案

- 检索和工具结果先形成结构化证据包：任务、用户事实、适用政策、条件、排除项、缺失信息、风险和引用。
- 回答前生成“结论、条件、步骤、时效、材料、异常和下一步”的内部计划。
- 回答后抽取金额、日期、时间范围、业务状态、允许/禁止操作等事实声明，逐条映射到知识或工具证据。
- 无证据声明不得输出：有可靠知识则补全，缺信息则追问，冲突或工具失败则明确说明并转人工。

### 示例

用户问“我的退款什么时候到账”：工具只能证明“已审核”，知识只能证明“审核通过后通常 1—3 个工作日原路退回”。最终回答可以组合这两条证据，但不能擅自声称“今天一定到账”。

### 验收

- 完整 Agent 回归目标从 78/100 提升到至少 81/100；
- 高风险继续保持 100%；
- 来源正确但必要信息缺失的样本减少；
- 金额、日期、订单/退款状态和操作承诺必须有证据；
- 若未达到目标，保留实验记录并回滚，不把候选层成绩冒充回答提升。

## 9. 后续技术路线

RAG v2 验证后，按回答效果证据依次考虑：结构化业务决策表、真实订单/退款/物流工具、分层会话记忆、Cross-Encoder Top-K 精排。当前不优先引入独立向量数据库、Graph RAG、自由循环 Agentic RAG 或微调；只有知识规模、关系复杂度或固定评测结果证明现架构成为瓶颈时再启用。

## 15. 技术优化主链确认

后续只沿回答能力的通用技术机制推进，数据处理暂停为配套工作，不再逐条修题：

1. 受约束 Hybrid 召回：关键词与向量召回融合，按租户、模型、active版本、业务类别、父子关系和动作证据约束候选；失败回退稳定来源。
2. 证据充分性判断：生成前判断当前证据是否足以回答结论、条件、时效、材料和下一步；不足时澄清、补检索或转人工，不允许猜测。
3. Corrective RAG：仅在证据不足时执行一次受限改写/重检索，禁止自由循环。
4. 多知识组合：单条知识不足时组合互补证据，做冲突、版本和适用条件检查。
5. 工具决策与回答审查：先判断是否必须读取订单/退款/物流事实，生成后检查来源、承诺、必要信息和转人工一致性。
6. 有界 Agentic RAG：把上述能力组织为有最大步数、最大工具次数、超时和稳定回退的状态机。

每一步只接受完整 Agent 同口径成绩：先同集 A/B 证明提升，再过既有94%回归和高风险100%保护；失败实验保留，但不进入默认或生产。
