# Hybrid RAG 前置设计（Step 7）

## 1. 当前检索基线

当前 `app/api/agent/respond/route.ts` 的检索不是向量 RAG：

1. `lib/intent-router.ts` 用规则与概率分类器确定四类业务意图。
2. `retrieveKnowledge` 从 `knowledge_documents` 读取同类 `active` 文档。
3. 使用 `keywordsJson` 与当前问题做字符串包含匹配并加权排序。
4. 若没有足够命中，回退到路由默认知识；随后将知识内容交给 Qwen 生成。

现有知识字段已经包含 Hybrid RAG 所需的第一批元数据：`category`、`state`、`risk`、`handoff`、`coverage`、`validFrom`、`validUntil`、`sourceType` 和 `keywordsJson`。当前缺少的是切片、embedding、向量索引和统一检索结果协议。

## 2. 目标方案

先实现可回滚的 Hybrid RAG，不立即替换线上策略：

- 关键词召回：保留现有可解释的关键词命中。
- 向量召回：为知识切片生成 embedding，按租户、业务类别、状态和有效期过滤。
- 融合排序：对关键词分、向量相似度、风险、版本有效性和意图一致性进行加权。
- 重排：对 Top-K 候选做轻量语义重排，输出统一 `RetrievalCandidate`。
- 影子评测：线上回答仍使用旧检索，同时记录 Hybrid 结果，与冻结 100 条评测集对照。

## 3. 实施顺序

1. 设计切片和检索结果类型，不改变生产回答。
2. 增加离线索引构建脚本和候选召回器。
3. 用同一评测集比较 lexical / vector / hybrid 的来源准确率、风险漏放率和延迟。
4. 只有 Hybrid 在来源准确率不下降且高风险通过率保持 100% 时，才逐步切换生产流量。

## 4. 暂不做的事情

- 暂不直接引入 Graph RAG：现阶段实体关系和流程图尚未稳定。
- 暂不让 Agent 自由循环调用检索：先把基础召回质量和审计协议做稳。
- 暂不删除规则路由：它仍是安全边界和低延迟兜底。

## 5. 验收指标

- 知识来源层级可接受准确率 ≥ 当前 78% 基线。
- 高风险通过率保持 100%。
- 范围外问题误路由不增加。
- P95 检索延迟可观测，整体延迟不出现不可解释的大幅回归。

## 6. 第一小步已完成

新增 `lib/retrieval.ts`，提供统一的 `RetrievalCandidate`、元数据过滤、关键词分、可选向量分和融合排序协议。它目前是影子评测能力，尚未接入生产回答，因此不会改变当前 78% 线上基线。

新增测试覆盖：

- inactive 文档和错误业务分类不会进入候选集；
- 关键词证据与向量证据可以融合排序；
- 即使没有关键词命中，也可以由足够高的语义分数选中候选。

自动化测试从 27/27 增加到 29/29，通过后再进入真实 Embedding 接入。

## 7. 第二小步已完成：Embedding 客户端

新增 `lib/embedding.ts`：

- 调用 OpenAI 兼容的 `/embeddings` 接口，可复用百炼的 `baseUrl`、API Key 和模型配置；
- 校验返回向量格式，并按 provider 返回的 `index` 恢复输入顺序；
- 提供余弦相似度计算；
- provider 失败或返回非法向量时显式报错，不静默伪造向量。

本小步使用测试 fetcher 验证协议，没有调用真实模型、没有消耗线上额度，也没有切换生产回答。自动化测试：30/30 通过。

## 8. 第三小步：真实向量索引脚本

新增 `scripts/build-embedding-index.mjs`。脚本在腾讯云容器内读取 active 知识，通过百炼 `qwen3.7-text-embedding` 生成向量，并写入持久化目录。它只生成索引，不改变 Agent 线上检索。

## 9. 真实向量索引与离线结果

- 使用腾讯云现有百炼 Key 和 `qwen3.7-text-embedding` 成功生成 25 份 active 知识向量。
- 向量维度：1024；索引大小约 532KB；索引写入容器持久化目录 `/data/knowledge-embeddings-qwen3.7-text-embedding.json`。
- 使用同一套 100 条评测问题生成查询向量，进行纯向量 Top-1 检索。
- 结果：46/100（46%），明显低于当前线上 78% 基线，因此不切换线上检索。
- 典型混淆：退款到账 vs 退货规则、发票申请 vs 发票税号修改、地址修改 vs 收件人手机号修改。
- 结论：向量检索能补充语义召回，但不能单独承担业务知识决策；必须与意图、关键词、元数据和知识层级融合。

## 10. 融合权重与门控实验

在同一 100 条问题上，仅比较 Top-1 知识来源命中：

- 纯关键词：84/100（84%）；
- 纯向量：46/100（46%）；
- 简单融合（关键词 + 向量权重 10）：61/100（61%）；
- 低向量权重 0.5：76/100（76%）；
- 关键词有命中时优先保留关键词，向量只补充无把握样本：79/100（79%）。

这组 79% 是“检索来源命中率”，不是线上完整 Agent 问答通过率，不能直接与线上 78% 画等号。它证明了门控融合比简单加权更合理，但还需要把候选结果接入完整 Agent 影子链路，重新评估回答、转人工和高风险指标。

## 11. 完整 Agent 影子对照

使用最近一次真实 Agent 回归结果作为当前实际来源，对同一批 100 条问题重新计算候选：

- 当前 Agent 严格知识来源命中：67/100（评测层级可接受口径为 78/100）；
- 关键词候选：84/100；
- 纯向量候选：46/100；
- 门控 Hybrid 候选：79/100；
- Hybrid 候选与当前 Agent 实际来源一致：73/100。

这里仍然只比较知识候选与来源，没有把 Hybrid 候选交给 Qwen 重新生成回答，也没有重新计算转人工、必要信息和安全指标。因此该结果只能证明“候选层有潜力”，不能宣称完整 Agent 质量已经提升。

## 12. 受控 Agent 影子生成

在 15 条小样本上，使用 Hybrid 候选知识重新调用真实 `qwen-plus`，提示词结构与线上一致：

- 当前 Agent 来源命中：13/15；
- Hybrid 来源命中：11/15；
- Hybrid 生成回答的必要信息检查通过：13/15。

Hybrid 暂未改善完整 Agent 结果，不能接入线上。当前主要问题是相邻父子知识的候选重排，而不是模型生成能力；下一步加入知识层级约束和候选置信度门控。

## 13. 知识层级约束实验

新增 `applyKnowledgeHierarchyGuard`：当子知识没有明确命中其操作关键词时，对其进行降权，优先保留父知识。

在同一 15 条小样本上重新调用真实 `qwen-plus`：

- 当前 Agent 来源命中：13/15；
- 加入层级约束的 Hybrid 来源命中：11/15；
- Hybrid 回答必要信息检查：12/15。

结果没有改善，暂不接入线上。说明简单的“子知识无关键词就降权”仍然过于粗糙，下一步需要结合意图、业务动作和父子知识条件判断进行重排。

## 14. 业务动作感知重排实验

新增动作感知重排：向量只负责补充候选，是否允许子知识替换父知识由当前问题中的明确业务动作决定。离线评测改用真实 Agent 路由，不再用期望来源推断类别；评分使用严格来源和层级可接受来源两套口径。

100 条结果：现网 86%、纯关键词 88%、纯向量 61%、旧 Hybrid 78%、动作重排 Hybrid 89%。动作重排相对现网仅改变 3 条，3 条改善、0 条退化。固定 15 条真实生成影子集上，现网与动作重排来源均为 14/15。

本轮仍不接生产回答。下一阶段建设生产影子检索 telemetry：记录索引模型/版本、候选 Top-K、关键词/向量/动作分、选择理由、与现网来源差异和检索延迟；积累真实请求后再决定灰度。

## 15. 生产影子检索可观测性

Step 7 第十小步已完成，生产回答仍由原关键词/规则检索提供知识，Hybrid 只在后台运行：

- 新增 D1 `knowledge_embeddings`、`embedding_index_versions` 与 `retrieval_shadow_runs`。向量按租户、模型和索引版本保存；Agent 先读取当前版本指针，只使用该版本的文档向量。
- 索引导入不使用 D1 不支持的显式 `BEGIN/COMMIT`。脚本先写完新版本的 inactive 向量，再切换当前版本指针，最后同步 active 标记；非事务导入中断不会让 Agent 读取半成品版本。
- 影子 Hybrid 与 Qwen 生成同时启动，并通过 Worker `waitUntil` 在响应后保活；主链路不等待影子结果。向量请求最多 5 秒，任何配置、索引、模型或写入异常都只形成 failed 记录。
- 每条有效请求按 `traceId` 记录现网来源、影子来源、是否变化、Top-K 关键词分/向量分/融合分/相对现网分差、业务动作判断、选择理由、Embedding 模型、索引版本、耗时和错误码。问候或无法形成稳定业务路由的请求记录为 skipped。
- 新增只读 `/api/retrieval/shadows`，按当前租户返回最近记录及 completed/failed/changed、变化率、平均延迟和 P95 延迟；最多返回 200 条。
- `RETRIEVAL_SHADOW_ENABLED=false` 时不读取向量、不写影子表，完整回到原行为；腾讯云当前显式开启用于观察真实流量。

线上验收样本中，现网继续选择 `KB-302`，影子候选为 `KB-301`；影子耗时 291ms，索引包含 25 份、1024 维真实向量，查询汇总为 1 条 completed、0 条 failed、1 条 changed。该结果只证明链路和差异可观测，不代表影子候选已经优于现网，也不构成切流依据。

下一步先积累足够真实请求，按业务类目复核候选变化样本与失败率；只有在同一冻结评测口径下来源准确率提升、高风险保持 100%、P95 可接受且人工抽检无退化时，才设计小流量灰度。

## 16. 影子样本复核与灰度证据门禁

Step 7 第十一小步已完成。本步不优化模型，也不切换生产检索，而是把真实流量证据变成可复核、可审计、不可被展示筛选误导的决策输入：

- 新增 `retrieval_shadow_reviews`，一个影子运行最多保留一条当前复核结论。只有 `quality_reviewer`、`product_admin`、`system_admin` 可以写入；只有 completed 且候选发生变化的样本可以复核。
- 结论为 improvement、regression、equivalent、inconclusive。退化和无法判断要求说明；所有新增或更新均记录操作者、时间、索引版本和审计事件。
- `/api/retrieval/shadows` 支持按状态、业务意图、索引版本、是否变化和复核结论筛选明细；整体分析只按索引版本确定 cohort，展示过滤不改变就绪门禁分母。
- 分析结果包含整体成功/失败/变化/P95，四类业务分布、各索引版本分布，以及待复核、改善、退化、等价和无法判断数量。
- `readyForGrayDesign` 只在单一索引版本同时满足以下证据时为 true：completed ≥ 200；退款、破损、地址、发票各 completed ≥ 25；取得改善/退化/等价明确结论的变化样本 ≥ 30，inconclusive 不计入；失败率 ≤ 1%；P95 ≤ 500ms；明确结论中的退化率 ≤ 5%、改善率 ≥ 60%。人工填写的正确知识编号还必须属于当前租户。

该门禁不是自动发布器，也不代表达到后可以直接切流。它只说明证据足以开始编写灰度设计；正式灰度仍需冻结版本、风险验收、人工审批、流量控制和一键回退。
